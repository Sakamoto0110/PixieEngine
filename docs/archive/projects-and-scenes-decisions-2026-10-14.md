## How the decision arrived

With PIXIE-TODO-003 to PIXIE-TODO-017 completed, the owner proposed that the
next step was a program to create a project that consumes the engine. At that
baseline every game was a sample inside the repository; the engine had no
install or export, and `add_subdirectory` from outside would have put a game's
binaries in the engine's `bin/`.

Claude answered with numbered questions first. The owner asked for answers
with a focus on the user's and developer's experience instead of questions.
Claude then proposed a `pixie` command on `PATH` (`pixie new`, `pixie run`,
`pixie edit`), a project file with the engine's path, and a `git init` on
creation.

The owner rejected it as too complicated: a `PATH` change does not work on
another machine. The owner set the flow (open the editor, New project, choose
the folder), left versioning to the user, and put this phase together with
scene serialization, which had been postponed on 2026-10-13. Claude redrew the
design around the editor, and the owner accepted it ("pode fazer").

## Decisions by the owner

- Projects are created and opened from the editor: New project, then a
  folder. No command-line tool or `PATH` change.
- A project must work on another machine.
- Versioning belongs to the user; the editor creates nothing for it.
- Scene serialization (part 3 of PIXIE-PROPOSAL-004) comes in the same phase.

## Decisions taken by Claude, accepted with the design

- A project never records the engine's location; the editor that opens it
  supplies the engine it runs from.
- A project starts without code: a generic C API library loads its scene, so a
  new project opens without a compiler. Code is added later from the editor,
  which builds it with CMake (found on `PATH` or through `vswhere`).
- An entity belongs to the scene when it has a stable ID in a `SceneId`
  component; entities generated by project code are not saved.
- Field descriptors learn to add and remove their component by type name,
  which serves loading, Behaviours with fields, and the editor's "add
  component".
- `Entity` fields are saved as stable IDs. Unknown components and unknown
  fields survive a load and save unchanged.
- Serialization lives in the `runtime` module; no `scene` boundary is created.
- Edit mode does not step; Play keeps the scene entities in memory and Stop
  builds the World again from them.
- The folder picker is drawn in ImGui, to keep the editor portable.
- `pixie_game()` gives every game its three targets, and the player's `main`
  moves into the engine.
- The samples become projects, and a CTest test builds a generated project, so
  the templates are exercised on every test run.
- Out of the phase: exporting a standalone build, prefabs, nested scenes, a
  binary format, reloading code without a restart, undo, and native dialogs.
